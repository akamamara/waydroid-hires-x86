# Port the HAL first, AudioFlinger last

## Verified corrections (2026-11-07): read this first

This section was checked against the real repos, using the GitHub API, raw source and the AUR RPC. It **supersedes** the rest of the report wherever they conflict. In particular, the NDK/`audio_hw.c` plan in "Tier 1" below **does not apply to LOS 24**.

**What the sources actually say**
- **The legacy HAL is gone.** WayDroid-ATV commit "audio: Remove legacy Audio HAL" (2026-09-22, SupeChicken666) deleted `audio/audio_hw.c`, `Android.bp` and the policy XML from `android_hardware_waydroid`. That repo has no `lineage-24.0` branch; the LOS 24 manifest (`manifest_scripts/manifests-37/02-waydroid.xml`) pulls its `lineage-23.0` branch.
- **LOS 24 ships the AOSP AIDL audio HAL with a PulseAudio backend.** `device.mk` has `PRODUCT_PACKAGES += com.android.hardware.audio`, a vendor APEX built from `WayDroid-ATV/android_hardware_interfaces` branch `lineage-24.0`, under `audio/aidl/default/`. ATV added `pulse/StreamPulse.cpp`, `pulse/Context.cpp`, `primary/StreamPrimaryPulse.cpp` and others (2026-09-20 to 09-24). It talks to libpulse directly, not through ALSA. This is the "Reworked Audio HAL" in release **20261017**, which is confirmed as "LineageOS 24.0, Android 17 QPR0", x86_64 only. The `device/manifest.xml` still declares HIDL `android.hardware.audio@7.1`, which looks like a leftover (inference).
- **The Reddit HAL patch is already done upstream in spirit.** `pulse/Utils.cpp` maps `FLOAT_32_BIT→PA_SAMPLE_FLOAT32`, `INT_24_BIT→S24LE`, `INT_32_BIT→S32LE` and `FIXED_Q_8_24→S24_32LE`, and the stream takes its rate from the requested config.
- **The real limit is the advertised profiles, and they come from the vendor XML.**
  - The vendor `primary_audio_policy_configuration.xml` lists only `AUDIO_FORMAT_PCM_16_BIT` at 8–48 kHz.
  - The HAL's `main.cpp` parses `audio_policy_configuration.xml` through `AudioPolicyConfigXmlConverter` and builds each `<module>` (except r_submix) from it. `Configuration.cpp` `getPrimaryConfiguration()` is only the fallback, and it has the same 16-bit/48 kHz limit.
  - `Module.cpp` refuses any port config outside those profiles (`findAudioProfile`).
  - audioserver asks the HAL for its policy config first (`loadFromApmAidlConfigWithFallback`), so the HAL and policy both follow the XML.
  - So **a vendor XML overlay alone should lift the limit, with no build.** This is not yet tested on a running container.
- **The AUR `waydroid-apple-music` package won't help here.** Its PKGBUILD builds the legacy `audio_hw.c` (pinned commit `407f9b6`) with NDK API 33 (Android 13) as a 32-bit i686 `audio.primary.waydroid.so` for `/vendor/lib/hw`. The LOS 24 ATV image has no legacy HAL to load it. Treat "works with any Waydroid image" as false for this image (inference from the removal).
- **The PRs are upstream Waydroid lineage-20 history, not ATV LOS 24.** PR #80 **was merged** (2026-11-02) into upstream `waydroid/android_hardware_waydroid` lineage-20. PR #91 is **still open**. Neither affects ATV LOS 24.
- **AudioFlinger lives in ATV's own fork.** `frameworks/av` comes from `WayDroid-ATV/android_frameworks_av` branch `lineage-24.0`, so that's where a DIRECT/UID patch would go.

**Revised plan, cheapest first**
1. **No build at all:** open an issue or PR on `WayDroid-ATV/android_hardware_interfaces` asking for hi-res profiles in `getPrimaryConfiguration()`. The patch is small, and the maintainer already builds and ships the images.
2. **Hi-res with no build:** add PCM_FLOAT profiles at 44.1–192 kHz to the "primary output" mixPort in an overlay copy of `/vendor/etc/primary_audio_policy_configuration.xml`. The mixer then runs at a hi-res rate, but it is not bit-perfect.
3. **Bit-perfect for Apple Music:** add a DIRECT mixPort in the same XML, again with no build. Apple Music never asks for DIRECT on its own, so audioserver still needs the UID patch in ATV's `frameworks/av` lineage-24.0 (`AudioFlinger::createTrack`). Build only `libaudioflinger` (full tree, zram plus swap) and overlay it. `docs/plans/` has the full plan.
4. **The Apple Music Wi-Fi/lossless check:** still unverified on LOS 24.

---

The most reliable way to bring this fix to Waydroid Android 17 / LineageOS 24.0 is to split it in two. The vendor half (the audio HAL plus `audio_policy_configuration.xml`) probably carries over cheaply: the AudioFlinger patch is only needed to force DIRECT output, so plain hi-res does not depend on it. You can rebuild this half on your 16 GB machine, probably without a full Android tree, and deploy it as a Waydroid overlay. The system half (the AudioFlinger patch that forces `AUDIO_OUTPUT_FLAG_DIRECT` for Apple Music's UID) is a different job. It is tied to the exact LOS 24 system build and has to be re-ported by hand against a heavily changed `frameworks/av`. It needs a full-tree build: locally with zram and swap, or on a rented VM for a few hours. Treat that half as optional until the vendor half alone shows it is not enough. Two things make the vendor-first route attractive. Upstream PR #80 already reimplements the original HAL change as a patch, and the AUR package `waydroid-apple-music` claims bit-perfect Apple Music from "patched audio HAL, container properties, and app settings" alone, with no framework patch, built with the NDK and working "with any Waydroid image". **One big caveat:** every researcher's web fetching was blocked, so no source file, diff, PKGBUILD or release page was actually opened. Everything below rests on search-result snippets and the local copy of the post. Several load-bearing facts are unverified and marked as such. Do the "verify first" checklist before you build anything.

## Three changes, of which only one is tied to the framework version

The original Android 13 fix changes three things. Only the local copy of the post documents them, because the author published binaries on Google Drive and no source diff. First, **the Waydroid HAL `audio_hw.c` forced S16_LE at 48 kHz.** The author added 16-, 24- and 32-bit cases with a 16-bit/48 kHz fallback, and later **FLOAT32**. Float was what made 24-bit DIRECT work, "because apple music internally uses Float32 format for 24bit audio". Second, the shipped `vendor/etc/audio_policy_configuration.xml` sets the primary output to `AUDIO_FORMAT_PCM_FLOAT` at 48000, and you can raise the rate. Third, **AudioFlinger was patched to add the DIRECT flag** to Apple Music's tracks, with the app identified by a UID read from `/data/local/tmp/apple_music_uid.txt`. The install is just `vendor/` and `system/` folders dropped into `/var/lib/waydroid/overlay/`, and the post says you can delete `system/` if Android's resampling is acceptable ([local post](https://www.reddit.com/r/waydroid/s/TjBa8AJyd3)).

PR #80 against upstream `lineage-20` ("honour the format and rate AudioFlinger requests", by kanya-approve) independently confirms the HAL diagnosis. It says `adev_open_output_stream()` hardcodes S16_LE at a fixed rate. The PR uses the requested format and rate instead and widens the primary mixPort to float plus rates up to 192 kHz. **It deliberately adds no DIRECT mixPort.** Its own test log shows a float format falling into `LOG_ALWAYS_FATAL`, the same FLOAT32 gap the Reddit author hit ([PR #80](https://github.com/waydroid/android_hardware_waydroid/pull/80)). PR #91 then restores a 4-period (about 85 ms) buffer after a bytes-to-frames change made audio through the pulse plugin choppy. It also states that since #80 AudioPolicyManager opens the mixer at the highest rate offered ([PR #91](https://github.com/waydroid/android_hardware_waydroid/pull/91)). Whether either PR was merged, or picked into WayDroid-ATV, is unknown.

The HAL reaches the host through alsa-lib's `"pulse"` PCM, using `waydroid.pulse_runtime_path` and `PULSE_RUNTIME_PATH`, and not through PipeWire directly ([CachyOS forum](https://discuss.cachyos.org/t/bit-perfect-audio-on-waydroid-using-bit-perfect-audio-from-waydroid/11294)). So host-side rate switching still depends on PipeWire's `default.clock.allowed-rates`, as in [Ivon's guide](https://ivonblog.com/en-us/posts/play-apple-music-android-on-linux/).

The Apple Music "fix" is mostly not audio. Lossless is refused because Waydroid's bridged network shows up as Ethernet. supechicken's A13 build solved that with virt-wifi, and an older workaround is `waydroid prop set persist.waydroid.fake_wifi <package>` ([Lemmy](https://lemmy.world/post/1771401); [waydroid#1514](https://github.com/waydroid/waydroid/issues/1514)). The network part is independent of the audio patches and has to be re-checked separately on LOS 24. One notes file says supechicken now runs the WayDroid-ATV org, which might mean virt-wifi carries over, but that is **unverified**. The "turn off animated art" step comes with no explanation from the author.

## Android 17 keeps the old HAL path alive, probably

The biggest structural risk is the HAL interface. From Android 14 the audio HAL is AIDL (`android.hardware.audio.core`). HIDL stopped at 7.1, and new features such as bit-perfect are AIDL-only ([AOSP AIDL/HIDL comparison](https://source.android.com/docs/core/audio/aidl-hidl-comp)). VINTF still supports deprecated HAL versions "for upgrading devices" ([AOSP FCM lifecycle](https://source.android.com/docs/core/architecture/vintf/fcm)). Android 17's FCM level is 202604 ([AOSP gitiles](https://android.googlesource.com/platform/hardware/interfaces/+/android17-release/compatibility_matrices)). Whether that matrix still lists HIDL audio **was not verified**. The evidence that Waydroid still uses HIDL is indirect: a vendor image built 2026-04-28 failed because `android.hardware.audio@2.0-service` was missing ([waydroid#2421](https://github.com/waydroid/waydroid/issues/2421)). If WayDroid-ATV's LOS 24 still wraps the legacy `audio_hw_device` C HAL, the switch-case patch ports almost as-is. If it moved to AIDL, the format logic has to be rewritten against `AudioFormatDescription`. The policy XML also stops mattering, because the configuration then comes from `IConfig`/`IModule` and not from `/vendor/etc`.

A second risk: WayDroid-ATV release **20261017 (LineageOS 24.0, Android 17 QPR0)** lists a "Reworked Audio HAL, which improves stability and brings slightly better audio latency performance". It ships x86_64 GAPPS/VANILLA system images and MAINLINE vendor images, installable with `waydroid init -f -c …/a17-qpr0/system -v …/a17-qpr0/vendor` against `waydroid-atv.github.io` ([release 20261017](https://github.com/WayDroid-ATV/waydroid-builds/releases/tag/20261017)). The sources conflict, though. A separate search said the newest release is 20260717 (LOS 23.2), and one snippet suggested the "reworked HAL" line might belong to an older release ([releases page](https://github.com/WayDroid-ATV/waydroid-builds/releases)). Either way, a reworked `audio_hw.c` means neither the Reddit binaries nor PR #80 will apply cleanly. You have to rebase by hand. Also note that the HAL lives in WayDroid-ATV's fork of **`android_hardware_waydroid` (`audio/audio_hw.c`)**, not in `android_vendor_waydroid`. The vendor repo holds the manifest generator, patches and build glue.

For the framework side, Android 14 added preferred mixer attributes with `AUDIO_OUTPUT_FLAG_BIT_PERFECT`. This is the official replacement for a UID hack, but it is documented for USB devices, is AIDL-HAL-only, and only applies if the app opts in ([AOSP preferred mixer attributes](https://source.android.com/docs/core/audio/preferred-mixer-attr)). Nothing found shows that Apple Music calls it. So on LOS 24 the realistic DIRECT options are two. You can declare a separate DIRECT mixPort (PCM_FLOAT/24-bit, hi-res rates) in the policy XML and test whether policy picks it. Or you can re-port the AudioFlinger hack to Android 17's `frameworks/av`, which has been restructured since 13.

## Tier 1: rebuild only the HAL, ship it as an overlay

Start here. It needs no Android tree if item 4 confirms the NDK approach. The NDK-only claim is an inference from the AUR package's `android-ndk` makedepend; the PKGBUILD itself was not read ([AUR](https://aur.archlinux.org/packages/waydroid-apple-music)). The plan: install the stock WayDroid-ATV LOS 24 images, then take `audio_hw.c` from the lineage-24.0 branch. Apply PR #80's logic by hand: use the requested format and rate, and map `AUDIO_FORMAT_PCM_FLOAT`→`SND_PCM_FORMAT_FLOAT_LE`, 24-bit→`S24_LE`/`S24_3LE`, and `PCM_32_BIT`→`S32_LE`. Add the missing float case so it never reaches `LOG_ALWAYS_FATAL`, and keep PR #91's 4-period buffer. Then compile with NDK clang for `x86_64-linux-android<API>`, using headers from AOSP `hardware/libhardware` and `system/media/audio`. `libcutils` is not in the NDK, so link against the copy pulled from the running image, or replace property calls with libc's `__system_property_get`. The vendor `.so` may link only VNDK/LL-NDK libraries, or dlopen fails with a namespace error. Overlays are layered on with overlayfs when `mount_overlays` is set in `/var/lib/waydroid/waydroid.cfg` ([gist](https://gist.github.com/aljustiet/92ccbed4d0b1be9b97c30a673ee01c37)), and a porter has replaced vendor libs exactly this way ([SailfishOS IRC log](https://irclogs.sailfishos.org/logs/%23sailfishos-porters/2025/%23sailfishos-porters.2025-08-29.log.html)). These deploy and check commands are inferred and not tested on LOS 24:

```bash
sudo install -Dm644 audio.primary.waydroid.so /var/lib/waydroid/overlay/vendor/lib64/hw/audio.primary.waydroid.so
sudo install -Dm644 audio_policy_configuration.xml /var/lib/waydroid/overlay/vendor/etc/audio_policy_configuration.xml
waydroid session stop && sudo systemctl restart waydroid-container
sudo waydroid shell -- dumpsys media.audio_flinger   # output thread Format / Sample rate / Flags
sudo waydroid shell -- logcat -b all | grep -iE 'audio|linker|avc'
```

In the same tier, try the cheap DIRECT experiment. Add a second mixPort with `AUDIO_OUTPUT_FLAG_DIRECT` and PCM_FLOAT plus 24-bit profiles at 44.1–192 kHz, then check `dumpsys` while Apple Music plays. If the thread shows DIRECT, you never need tier 2. Roll back by deleting the overlay files and restarting. Leave `overlay_rw` alone.

## Tier 2: full-tree single-module builds, local or rented

If NDK linking fails, or the HAL turns out to be AIDL, build `m audio.primary.waydroid` in a lunch'd LOS 24 tree. If DIRECT does not engage through XML, also re-port the UID hack and run `m libaudioflinger`. Build both against the exact manifest and security tag of the image you run, because "you can't run newer vndk with older system" ([SailfishOS IRC log](https://irclogs.sailfishos.org/logs/%23sailfishos-porters/2025/%23sailfishos-porters.2025-08-29.log.html)). The flow follows the documented Waydroid recipe of `repo init` LineageOS with `--git-lfs`, `generate-manifest.sh`, sync, `lunch`, then build ([Waydroid docs](https://docs.waydro.id/development/compile-waydroid-lineage-os-based-images); [WayDroid-ATV BUILDING.md](https://github.com/WayDroid-ATV/waydroid-androidtv-builds/blob/main/BUILDING.md)). A shallow clone cut an Android 11 checkout from about 105 GB to about 77 GB, while partial clone barely helped ([junsun.net](https://junsun.net/wordpress/2021/01/android-aosp-repo-checkout-method-and-size-comparison/)). Plan for at least 200 GB free; that figure is an estimate. An inferred recipe:

```bash
repo init -u https://github.com/LineageOS/android.git -b lineage-24.0 --git-lfs --depth=1 --no-clone-bundle
# add WayDroid-ATV local_manifests via generate-manifest.sh (verify path), then:
repo sync -c --no-tags --no-clone-bundle --optimized-fetch -j8
source build/envsetup.sh && apply-waydroid-patches
lunch lineage_waydroid_x86_64-<release>-userdebug   # token unknown; read lunch output
m nothing                                           # test whether Soong analysis survives
m -j6 audio.primary.waydroid libaudioflinger
```

On 16 GB the danger is Soong analysis, not compiling. Google now lists 64 GB as the minimum ([AOSP requirements](https://source.android.com/docs/setup/requirements?hl=ko)). `soong_build` gets OOM-killed on 16 GB machines without swap ([android-building](https://groups.google.com/g/android-building/c/5G2l5JR3jWE)), and `m <module>` still pays the full analysis cost. A low-RAM guide reports 16 GB is workable with zram, found lz4 beat zstd, and recommends timing `m nothing` first ([dev.to](https://dev.to/merinorus/building-android-roms-on-limited-ram-zram-vs-zswap-comparison-42jd)). On CachyOS, raise the zram size (16–24 GB lz4) and add a 32 GB NVMe swapfile at lower priority; these numbers are estimates. If analysis still thrashes, rent a machine. A Hetzner CCX63 (48 vCPU, 192 GB RAM) costs about €1.37/h after the June 2026 increase, though price sites disagree ([privatedevops](https://privatedevops.com/news/hetzner-june-2026-cloud-price-increase-what-to-do)). A few hours for sync plus build would be roughly €3–5, an estimate. crave.io is free but approval-gated and has a reported 6-hour timeout ([fossontop](https://fossontop-aosp.pages.dev/crave/getting-started/introduction)). GitHub runners are too small for a full tree but fine for the tier-1 NDK build ([dzombak](https://www.dzombak.com/blog/2024/09/freeing-disk-space-on-github-actions-runners/)).

## Conclusion

The port is less a port than a rebuild with a much smaller framework part. The Android 13 author needed a framework hack because DIRECT would not engage and float was missing. Both problems sit in the HAL and the policy config, which upstream has since half-solved. So the AudioFlinger patch is probably a fallback now, not the core of the fix. The answer to the HIDL-vs-AIDL question (checklist items 2 and 8) decides almost everything that follows. On HIDL, tier 1 is an afternoon of work. On AIDL, the XML overlay stops mattering, the switch-case patch must be rewritten, and Android 14's BIT_PERFECT route becomes reachable, which is cleaner than any UID hack.

If you get it working, open a PR against WayDroid-ATV's `android_hardware_waydroid` lineage-24.0. It is the durable fix: no ATV-specific audio work turned up, and every overlay you keep locally breaks on the next image update.
